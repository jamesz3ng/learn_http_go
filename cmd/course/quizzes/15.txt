# Stage 15: Middleware

## What is the usual Go type of an HTTP middleware?
* func(http.Handler) http.Handler
- func(http.ResponseWriter, *http.Request) error
- http.RoundTripper
- interface{ Before(); After() }
> A middleware takes the next handler and returns a new handler that wraps
> it. Chaining is just function composition.

## handler := a(b(c(mux))). Which middleware's code runs FIRST for a request?
* a
- c
- mux
> The outermost wrapper receives the request first, calls the next one, and
> finishes last.

## A handler panics and there's no recovery middleware. What does the client get?
- 500 Internal Server Error, written by net/http
* The connection is closed with no response
- The process crashes and all clients are disconnected
> net/http recovers handler panics per connection, logs the stack trace and
> closes that connection,
> so the client sees an empty reply, not a 500. The server keeps running.

## Your wrapper struct embeds http.ResponseWriter and adds nothing else. What does w.(http.Flusher) return in a handler?
* ok == false: only the ResponseWriter interface's methods are promoted, so Flush is hidden
- ok == true: embedding promotes all methods of the underlying value
> Embedding an interface promotes only that interface's methods. The dynamic
> type's extra methods (Flush, Hijack, ReadFrom) are hidden.

## How does http.ResponseController find Flush through middleware wrappers?
* It calls each wrapper's Unwrap() method in turn
- It uses reflection to walk embedded fields
- It doesn't: wrappers must implement Flush themselves
> It calls the wrapper's Unwrap() http.ResponseWriter method, repeatedly,
> until it finds a writer that supports the operation.
> Give every ResponseWriter wrapper an Unwrap method, and use
> http.NewResponseController(w).Flush() in handlers.

## A handler panics AFTER writing part of the body. What should recovery middleware do?
- Write a 500 status and an error body
* Abort the response, e.g. panic(http.ErrAbortHandler)
- Log it and return normally from the handler
> It's too late for a 500: the status line was already sent. Aborting makes
> the client see the response fail. Returning normally would make a truncated
> response look successful. ErrAbortHandler closes the connection without a
> stack-trace log.

## Why use an unexported type (e.g. `type ctxKey int`) as a context key?
* No other package can create a key that collides with it
- context.WithValue requires a struct or int key type
- Lookups with unexported key types are faster than strings
> Context keys compare by type and value. A string key like "id" could be
> used by any package by accident, but no other package can create a value
> of your unexported type, so keys from different packages never collide.

## Recovery runs OUTSIDE the logging middleware: requestID(recover(log(mux))), with the Reading's logRequests (it logs after next.ServeHTTP returns, without defer). What's logged for a panicking request?
* No access-log record at all
- A record with status 500
- A record with status 200
> The panic unwinds through the logger before it can log; recovery only
> catches it further out. Put recovery inside logging so the logger sees the
> 500 that recovery wrote.

## r.WithContext(ctx) returns...
* A shallow copy of r with the new context
- r itself, modified in place
- A deep copy of r, including headers and body
> r itself is unchanged. Request values should be treated as immutable in
> middleware. WithContext gives a new *Request sharing the same headers, body,
> etc.

## Which slog call is the more efficient form for hot paths?
* logger.LogAttrs(ctx, slog.LevelInfo, "request", slog.Int("status", 200))
- logger.Info("request", "status", 200)
- logger.Log(ctx, slog.LevelInfo, "request", "status", 200)
- log.Printf("request status=%d", 200)
> The slog forms all produce the same structured record; LogAttrs, which
> takes only typed slog.Attr values, is the efficient form for hot paths.
