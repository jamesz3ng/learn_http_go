# Stage 16: RoundTrippers: client middleware

## Which single method does http.RoundTripper require?
= RoundTrip
= RoundTrip(*Request) (*Response, error)
= RoundTrip(*http.Request) (*http.Response, error)
= RoundTrip(req)
> RoundTrip(*http.Request) (*http.Response, error): one HTTP exchange.

## A RoundTripper receives a 500 response from the server. What should it return?
* The response with err == nil
- nil and an error describing the 500
- It depends on the method
> The contract says RoundTrip must not interpret the response: getting a
> response, whatever its status, is success at this layer.

## Why must a RoundTripper clone the request before setting a header?
* A RoundTripper must not modify the caller's request
- Headers can't be set on a request once it's built
- Clone makes the request faster to send
> The caller may reuse or inspect its request afterwards.
> req.Clone(ctx) deep-copies the headers (and more), so changes don't leak
> back to the caller. The body is still shared.

## Which failures are generally safe and sensible to retry automatically for a GET?
* A connection reset or refused
* 503 Service Unavailable
* 429 Too Many Requests
- 404 Not Found
- 400 Bad Request
- context.Canceled
- A TLS certificate verification error
> Transient failures may succeed later. 4xx errors mean the request itself is
> wrong, a bad certificate won't fix itself, and a cancelled context means
> the caller has given up.

## Why shouldn't a generic retry transport retry POST requests?
* POST isn't idempotent, so the action may run twice
- POST bodies can never be replayed on a retry
- Servers always reject a retried POST
> If the first attempt reached the server, retrying may perform the action
> twice. Only retry non-idempotent requests when the server can deduplicate
> them, e.g. with an Idempotency-Key header.

## On a retry, where does the request body come from?
- req.Body again
* req.GetBody()
- The response body
- It isn't sent on retries
> The first attempt consumed (and closed) req.Body. GetBody returns a fresh
> reader with the same content. It is set
> automatically for *bytes.Buffer, *bytes.Reader and *strings.Reader bodies.

## Why add jitter to exponential backoff?
* So clients that failed together don't retry in sync
- To make retry timing deterministic in tests
- Because timers aren't accurate enough without it
> Without jitter, clients that failed together all retry at the same instant
> (a thundering herd). Randomising the delay spreads retries out, giving an
> overloaded server a chance to recover.

## Why is `time.Sleep(delay)` a poor way to wait between retries?
* It ignores context cancellation
- Sleep can wake up seconds too early
- It blocks every other goroutine as well
> A cancelled request keeps sleeping until the delay is over. Instead,
> select on a timer and req.Context().Done() so cancellation takes effect
> immediately.

## You retry after a 503 without draining and closing its body. What's the cost?
* The 503's connection can't go back to the pool
- Nothing: the next RoundTrip reuses it anyway
- The retry reads the old 503 body by mistake
> Each retry then opens a new connection, and the old one leaks until the
> body is closed. Always drain and close responses you discard.

## A logging transport is placed INSIDE a retry transport. With 2 retries, how many log lines does one call produce?
* 3
- 1
- 2
> One line per attempt: the retry transport calls the inner transport once
> per attempt (1 + 2 retries). Placed
> outside, the logger would see only the final result.
