# Stage 21: Files, ranges and uploads

## A client sends If-None-Match: "abc" and the resource's ETag is still "abc". What's the response?
* 304 Not Modified, with no body
- 200 OK with the full body
- 412 Precondition Failed
- 204 No Content
> The client's cached copy is current, so the server says so without
> resending the content.

## Which status code means "here's the part of the content you asked for with Range"?
= 206
= 206 Partial Content
> 206 Partial Content, with a Content-Range header such as
> "bytes 0-4/11". 416 means the requested range can't be satisfied.

## What do you need to do so http.ServeContent answers If-None-Match requests?
* Set the ETag response header before calling ServeContent
- Pass the ETag as an argument
- Nothing: it computes ETags automatically
- Implement If-None-Match yourself
> ServeContent reads the ETag from w.Header() to evaluate If-Match,
> If-None-Match and If-Range. It never computes one itself.

## Why does ServeContent take an io.ReadSeeker rather than an io.Reader?
* To jump straight to the offset a Range asks for
- To read the content twice, once to compute an ETag
- Because only files can be served, and files can seek
> Seeking lets it serve any byte range without reading from the start, and
> Seek(0, io.SeekEnd) gives it the length.

## By default, what does http.FileServer do for a directory without index.html?
* Generates an HTML listing of its contents
- Returns 404
- Returns 403
- Redirects to the parent directory
> That's convenient for development but often unwanted in production. Wrap
> the fs.FS to hide directories without an index.

## What does http.StripPrefix("/static", h) do?
* Removes "/static" from the request path before calling h
- Strips "/static" from URLs in h's responses
- Registers h on the default mux under /static
> So the file server sees "/app.js" for a request to "/static/app.js". If
> the path doesn't start with the prefix, it answers 404 instead.

## Why use r.MultipartReader() instead of r.ParseMultipartForm() for large uploads?
* It streams each part as it arrives
- It's the only way to get the uploaded file names
- ParseMultipartForm can't read file parts at all
> ParseMultipartForm buffers the whole form first; MultipartReader lets you
> process each part as a stream (hashing, writing to storage...), so files
> never need to be held in memory or temp files.

## A part's Content-Type says image/png. Should a server trust it?
- Yes: browsers set it from the file's real contents
* No: it's whatever the client chose to send
- Yes: multipart.Reader checks it against the bytes
> Clients can claim anything. If the type matters, sniff the bytes with
> http.DetectContentType: the first 512 bytes give you the server's own opinion.

## Which status fits "this endpoint only accepts multipart/form-data, and you sent JSON"?
- 400 Bad Request
* 415 Unsupported Media Type
- 406 Not Acceptable
- 422 Unprocessable Content
> 415 is about the request's Content-Type. 406 is about the response
> formats the client will accept.

## What's the difference between a strong ETag "abc" and a weak one W/"abc"?
* Strong means byte-identical; weak, equivalent in meaning
- Weak ETags are shorter and cheaper to compare
- Strong ETags must be cryptographic hashes
> A weak ETag is good enough for caching, not for Range.
> Range requests (If-Range) and If-Match require strong comparison; weak
> validators only work for If-None-Match.
