# Stage 25: Connection pooling and httptrace

## What is the effective default of Transport.MaxIdleConnsPerHost?
= 2
> Zero means DefaultMaxIdleConnsPerHost, which is 2: too few for concurrent
> clients that talk to one host.

## 50 workers share a transport with the default MaxIdleConnsPerHost and hit one host. What happens as responses finish?
* Only 2 stay idle; later requests dial new connections
- All 50 connections are kept idle for reuse
- Requests queue for one of the 2 pooled connections
> Only 2 connections are kept idle; excess idle connections are closed, so
> later requests keep dialling new ones. MaxConnsPerHost (unlimited by default)
> is the setting that would make requests wait instead.

## Which conditions must hold for an HTTP/1.1 connection to go back into the pool?
* The response body was read to EOF
* Neither side asked to close the connection (keep-alive)
- The body was closed without reading it to EOF
- The request used GET
> Reaching EOF is what hands the connection back to the pool. Closing a body
> that wasn't fully read discards the connection, as does Connection: close.
> (Always Close anyway: it's how you release a body you don't read.)

## How do you find out whether one specific request reused a pooled connection?
* An httptrace.ClientTrace with a GotConn hook
- Checking resp.Header.Get("Connection")
- Calling Stats() on the http.Transport
> Attach the trace with httptrace.WithClientTrace(ctx, trace) and check
> GotConnInfo.Reused in the hook.
> httptrace exposes per-request hooks for DNS, connect, TLS, getting a
> connection, writing the request, the first response byte, and more.

## Over HTTP/2, roughly how many connections does a Go client keep to one host under concurrency?
* Usually one, shared by all requests
- One per concurrent request
- Two, as MaxIdleConnsPerHost is 2
> Requests are multiplexed as streams on one connection.
> HTTP/2 multiplexing makes most of the HTTP/1.1 pooling problem disappear.

## What does MaxConnsPerHost limit?
* All connections to a host: dialling, active and idle
- Only the idle connections kept for a host
- The number of requests per second to a host
> It's a hard cap on the total number of connections to a host; when
> reached, new requests queue until a
> connection is free.

## Why report p99 latency rather than only the average?
* Averages hide the slow tail that users hit
- p99 is cheaper to compute than an average
- p99 is always lower, so the results look better
> Percentiles show the tail that averages hide.
> If 1% of requests take 2 seconds, many users see it, especially on pages
> making many requests.

## In a worker-pool load generator, what bounds the number of requests in flight?
* The number of worker goroutines
- The size of the jobs channel
- GOMAXPROCS
> Each worker sends one request at a time, so in-flight requests never
> exceed the worker count.

## What is "coordinated omission" in load testing?
* Under-measuring latency because sends pause in stalls
- Forgetting to close response bodies between requests
- Letting workers share one connection by mistake
> A closed-loop tester sends fewer requests while the server stalls, so
> measured latency underestimates what users would see.
> Open-loop testing (sending on a schedule and measuring from the scheduled
> time) avoids it.
