# Stage 20: Consuming streams

## What does io.ReadAll(resp.Body) do on an endless event stream?
* Blocks until the stream ends, buffering it all
- Returns the first event once it's complete
- Returns an error, as there's no Content-Length
> ReadAll waits for EOF, so it blocks forever (or until the connection or a
> timeout ends), buffering everything in memory. Process streams incrementally
> with bufio.Scanner or bufio.Reader instead.

## What is bufio.Scanner's default maximum line length?
- 4 KiB
* 64 KiB
- 1 MiB
- Unlimited
> The default is bufio.MaxScanTokenSize. Longer lines make Scan stop with
> bufio.ErrTooLong. Call sc.Buffer(buf, max) to raise the limit.

## Two SSE lines "data: a" and "data: b" belong to one event. What is its data?
- "ab"
* "a\nb"
- "b"
- Two separate events
> Multiple data fields are joined with newlines.

## The caller cancels ctx while Watch is blocked reading. What should Watch return?
* ctx.Err(), i.e. context.Canceled
- The read error the cancellation caused
- nil, since the caller asked to stop
> The read error is a side effect of the cancellation. The caller asked to
> stop and should get the error that says so.

## How does Watch make the server stop sending when the callback returns an error?
* By returning, so the deferred Body.Close runs
- By sending a STOP event back to the server
- By calling cancel on the server's context
> Its `defer resp.Body.Close()` then runs. Closing a response body before EOF
> closes the connection; the server's handler sees its context cancelled.

## Why is a callback API (fn func(Event) error) simpler to get right than returning a channel?
* No goroutine to leak or channel to close
- Channels can't carry struct values like Event
- Callbacks are faster than channel receives
> A callback also gives natural back-pressure: the next event isn't read until
> fn returns. A channel API needs a goroutine, rules about who closes what,
> and a way to report errors. It's easy to layer one on top of a callback API.

## How can a JSON decoder tell an absent "value" field from "value": ""?
* Decode into a *string field
- Decode into a string and check for ""
- Add `json:",omitempty"` to the string field
> Pointer fields stay nil when the key is missing, and point at "" when it
> is present but empty.

## Which bounds a long-lived stream best?
* A context the caller cancels
- http.Client.Timeout
- Transport.ResponseHeaderTimeout alone
> A cancellable context, possibly plus an idle timeout between events, stops
> the stream only when it should. Client.Timeout limits the total time,
> including the body, so it kills long streams. ResponseHeaderTimeout only
> covers the wait for headers.
