# Stage 19: Streaming responses and SSE

## A handler writes a short line, then sleeps 5s, then writes more. Without flushing, when does the client get the first line?
- Immediately
* When the handler returns (or the write buffer fills)
- After exactly 5 seconds
> ResponseWriter buffers output. Flush (via http.NewResponseController) to
> send it immediately.

## A handler flushes after its first write and keeps writing. How is the HTTP/1.1 response framed?
* Transfer-Encoding: chunked, chosen automatically because the length isn't known yet
- Content-Length, computed when the handler returns
- The connection is closed to mark the end
> Once headers go out before the handler finishes, Go can't know the length,
> so it uses chunked encoding.

## How do you lift the server's WriteTimeout for one long-lived streaming response?
* http.NewResponseController(w).SetWriteDeadline(time.Time{})
- Set srv.WriteTimeout = 0 inside the handler
- Call w.WriteHeader(200) early
- It's impossible
> The zero time means "no deadline", for this response only.

## In the SSE format, what ends an event?
* A blank line
- The next "event:" line
- A null byte
- Closing the connection
> Fields accumulate until an empty line, which dispatches the event.

## Which SSE field lets a reconnecting client resume where it left off?
= id
= id:
> The browser remembers the last id and sends it as the Last-Event-ID request
> header when it reconnects.

## Lines starting with ":" in an SSE stream are...
* Comments, ignored by clients; useful as keepalives
- Field continuations
- Event names
> Comments keep idle connections from being closed by proxies and load
> balancers.

## Why must publishing to watchers never block?
* Otherwise one slow watcher would stall every PUT and DELETE for all clients
- Because channels can't block
- Because the race detector forbids it
> Use a non-blocking send (select with default) and drop watchers whose
> buffer is full.

## Why subscribe BEFORE sending the 200 headers on /watch?
* Once the client sees headers it may start making changes; subscribing later could miss events in between
- Headers can't be sent before subscribing
- To get a lower id
> Order the steps so that "response started" implies "subscribed".

## Why publish while still holding the store's lock?
* So events are delivered in the same order as the changes they describe
- Channels require a lock
- It's faster
> If two PUTs published after unlocking, their events could be reordered
> relative to the changes. Publishing is non-blocking, so holding the lock is
> cheap.

## Which is the correct way to tell, inside a streaming loop, that the client has gone?
* <-r.Context().Done() fires (and/or Write/Flush returns an error)
- r.Body returns io.EOF
- w.Header() becomes nil
> The server cancels the request context on disconnect. Write and Flush
> errors are the other signal.
